Header Redesign - Chronicle.com

A context-aware header system designed through stakeholder workshops that serves users' goals on different page types

Role:
Lead Product Designer

Timeline:
2023 - 2024

Team:
3 Engineers, 1 Product Manager, C-Suite Stakeholders

Tools:
Figma, FigJam, Adobe Analytics

The Challenge

Chronicle.com needed a header system that could serve diverse user needs across different page types, from breaking news to in-depth reports to data tools. The existing header was one-size-fits-all, forcing the same navigation experience on readers regardless of their goals or the content they were engaging with.

Key problems:

  • Competing priorities: Stakeholders across departments had different ideas about what should be prominent in the header
  • Scalability concerns: Adding new features or promotions required custom header modifications
  • Mobile experience: The mobile experience had several accessibility issues and was difficult to navigate

The goal was to design a header system (not just a header) that could get users where they wanted to go, while balancing business priorities and fixing key accessibility and usability issues.

Research & Analysis

Quant Analysis

I started by analyzing user behavior in Adobe Analytics to understand how people actually navigated the site and used the existing header. This revealed patterns in navigation flows, common entry and exit points, and which header elements were being clicked (or ignored) on different page types (smashing some previous assumptions).

Key insights:

  • Users navigating from the homepage had different needs than those landing on article pages from search, email, or social media - leading to drops in recirculation
  • Certain header elements had high visibility but low click-through, suggesting they were creating visual noise without adding value
  • Mobile users often bypassed header elements entirely to get to the content quicker
  • Multiple elements that we assumed were effective were actually performing poorly, leaving the door open for us to think about different ways to accomplish the goals of those components

Stakeholder Workshops

Rebranding

Shortly after designing a first iteration, we were given new brand guidelines to work with. This rebrand gave me the chance to conduct design workshops with key business stakeholders and C-suite executives before jumping into solutions.

I led sessions that were structured to focus exclusively on analysis, goals, and priorities. Stakeholders were explicitly discouraged from proposing solutions or debating design details.

Workshop Structure

Over three sessions, I facilitated exercises that helped stakeholders:

  • Articulate their department's goals for the header without prescribing solutions
  • Prioritize competing objectives through ranked voting and discussion
  • Identify user scenarios where the header needed to serve different needs
  • Define success metrics that would guide design decisions

Workshop Outcomes

We emerged from these workshops with firm requirements, clear scope, and most importantly, a prioritized list of goals that everyone had agreed upon. This alignment proved invaluable later when making difficult trade-off decisions during the design process and helped avoid scope creep.

The workshops also revealed something crucial: different page types needed different header configurations. A reader browsing the homepage had different navigation needs than someone reading an in-depth article or using a data tool.

The Solution: A Responsive Header System

Core Header + Slim Header Architecture

Rather than designing a single header, I designed a flexible header system with two core components that work together to serve users' needs on each page type.

The system consists of two states:

The Core Header: Appears at the top of pages when users first land, providing full navigation context and key actions. It includes all primary navigation elements, search, reader relationship, and account access.

The Slim Header: Replaces the core header on scroll, becoming a sticky navigation bar that stays with users as they read or interact with content. This slim version maintains essential navigation while minimizing screen real estate and can provide page-specific options such as recirculation or social sharing.

This two-header approach means:

  • Navigation doesn't disappear or take up valuable reading space once they start engaging with content
  • Each page type can feature different options in the slim header based on what users need in that context
  • We can A/B test different slim header configurations without rebuilding the entire header

Customization for Page Context

The slim header adapts based on page type:

  • Article pages: Feature sharing tools and related content navigation
  • Account and workflow pages: Communicate's reader relationshipa and provides account options
  • Homepage and default: Content promotion and account access

This flexibility means users always have relevant tools at hand without cluttering the interface with options they won't use in that context.

Mobile Version

Mobile required a different approach. With limited screen real estate and user feedback consistently requesting a cleaner reading experience, I prioritized simplicity over feature parity with desktop.

Mobile Strategy:

  • Streamlined navigation menu with only essential top-level categories
  • Prioritized search and account access as primary actions
  • Minimal sticky header that appears on scroll-up only (disappears on scroll-down to maximize reading space)

This approach respected the mobile reading experience while ensuring users could still access core functionality when needed. Testing showed that mobile users preferred this lightweight approach and were able to find navigation options when they needed them without feeling overwhelmed by options when they didn't.

The Result

The new header system launched as an MVP that established the flexible architecture for future iterations.

What we achieved:

  • Flexible system architecture that can adapt to different page types and user needs without requiring full redesigns
  • Improved stakeholder alignment through the workshop process, making future header changes easier to implement with buy-in
  • Cleaner mobile experience that respects reading flow while maintaining navigation accessibility
  • Foundation for navigation system rework that informed broader site architecture improvements
  • More recirculation opportunities to show more relevant content to keep users engaged and informed

Impact: The header system proved its value by enabling rapid experimentation with different slim header configurations for A/B testing. Most importantly, the system laid groundwork for a complete navigation architecture overhaul that's currently in progress.

What I Learned

Constraints can be opportunities. The mid-project rebrand that forced us to restart actually led to better stakeholder alignment and a stronger final solution than we would have achieved by pushing through with the original design.

Design workshops need clear guardrails. By explicitly prohibiting solution discussion and focusing on goals and priorities, we avoided the typical "design by committee" problems and gave stakeholders productive ways to contribute their expertise.

Systems thinking pays off. Designing a system rather than a single header created flexibility that continues to provide value as the site evolves. The investment in architecture upfront enabled faster iteration later.

Context is everything. The realization that different page types need different headers seems obvious in retrospect, but it was a breakthrough that came from really listening to analytics data and user behavior rather than assuming one solution could serve all needs.

Mobile isn't just small desktop. Respecting mobile as its own experience with different constraints and user expectations led to a better solution than trying to cram desktop functionality into a small screen.
